# 不與正式規格流程整合，只定義交棒規則

**選了什麼**

doc-system-kit（prototype 用）與正式規格流程各自跑，中間只定義**交棒時交什麼**。
兩邊的工具可以互搬，流程不合併。

**為什麼不整合**

三個基數對不上，而且都是硬的：

| | 正式規格流程 | doc-system-kit |
|---|---|---|
| 範圍 | 一個 repo 裝多個專案的規格 | 移植到每一個專案內部 |
| 受眾 | 主管、美術、程式 —— 看網頁，不 clone、不用 git | AI 和開發者 —— 在 repo 裡讀原始檔 |
| 節奏 | 以功能為單位，MR ＋ 簡報審查（週／月級） | 以一次收工為單位，Stop hook 擋（小時級） |

合併的後果很具體：收工 hook 裝進規格 repo 之後，企劃改一句話就被擋著要回填。

而且兩邊的核心機制對彼此**完全無用** —— 區塊契約解的是「呈現層被洗掉」，
kit 沒有呈現層；收工 hook 解的是「程式改了文件沒跟上」，規格 repo 沒有程式碼。

**它們是接力不是並行**

正式規格流程的第一個階段本來就是概念發想與原型，而且通常已經定調
「原型與正式規格 repo 分開存放」——因為原型是拋棄式的、可能多版本並存，
混進去會污染規格的 git 歷史。kit 就長在那一格。

**交棒清單**

| 交 | 不交 |
|---|---|
| DESIGN 的「要驗證的假設」「健檢」「已排除的方案」 | TECH（正式開發會重寫） |
| PLAN 的「已排除的技術路線」 | 時序 entry（流水帳） |
| `decisions/` 全部 —— **這是最不可能被重建的東西** | |

⚠️ **數值要標明是假值還是定案值。** prototype 交棒時最常見的失真，
就是假值被當成定案值抄進正式規格。

**封存原則**

prototype 交棒後**一律封存，不捨棄**。原地凍結打 tag、每份文件 frontmatter
加 `archived` 與 `superseded-by`（改 frontmatter 不動內文，不違反「只追加」）、
正式規格那側要有回鏈。

捨棄的唯一情況：`decisions/` 與技術評估都是空的 —— 那代表沒有可陳述的結論。

> 為什麼不捨棄：commit body 裡的「決策：X／因為 Y」**提取不出來**，
> 它們散在 git log 裡、沒有結構。捨棄 repo 等於把整週為了寫好 commit body 付的成本丟掉。
