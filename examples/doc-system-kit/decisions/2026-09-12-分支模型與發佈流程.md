# 兩條長命分支 ＋ 一次性試玩分支，產出物不進 git

**問題是什麼**

這一包已經規範了文件怎麼寫、commit body 怎麼寫、收工怎麼擋，**唯獨分支沒有規範**。

實際狀況是慣例早就存在：`git log` 裡穩定出現 `feat/*`、`chore/*`，PR 合進 `main`，
四個分支名稱形狀完全一致。但**沒有任何一份文件寫下來** ——
它只存在於「上次是怎麼做的」這個記憶裡。

那正是本包一直在治的狀態：**能動，只是已經不對了**，而且第二個人進來時
只能猜，猜錯不會報錯。

同時使用者的產品是遊戲，有兩件既有慣例沒涵蓋的需求：
一條代表**已發佈內容**的線，以及**試玩版輸出**用的分支。

**選了什麼**

| 決定 | 內容 |
|---|---|
| 長命分支 | 只有兩條：`main`（開發）、`stable`（已發佈） |
| 短命分支 | `feat/` `fix/` `docs/` `chore/` `refactor/` `hotfix/` `demo/` |
| 命名 | `<type>/<英文-kebab-slug>`，**type 與 commit type 共用同一套字彙** |
| 試玩分支 | 一次性：切 → 減 → 封 → 打 tag → 刪分支。**不合回任何地方** |
| tag | 正式版 semver `v0.3.1`；試玩版 `demo-<YYYY-MM>-<場次>`。**兩套不混用** |
| 產出物 | build 不進 git，走發佈平台，用 tag 對應 |
| 機制 | **沒有 hook。只有文字** |

正本放 [../../../core/starter/AGENTS.md](../../../core/starter/AGENTS.md) 的「分支與發佈」——
因為那一份會被複製進下游專案，是 AI 讀得到的唯一一份。
操作步驟與「為什麼」分別在 [../../../core/分支與發佈.md](../../../core/分支與發佈.md)
與 [../../../README.md](../../../README.md)，**分支表只有一份，其餘用連結指過去**。

**沒選的路**

| 沒選 | 為什麼 |
|---|---|
| **GitFlow（多一條 `develop` 與 `release/*`）** | `release/*` 是為了解決「發佈前凍結、同時繼續開發下一版」的並行。個人與小團隊沒有這個並行 —— 你就是那個人。加了只是多一層每次發佈都要維護的東西，而**它擋不掉任何實際會發生的錯誤** |
| **長期維護的平行 `demo` 分支** | 長期存在就要持續從 `main` 跟進，於是每次跟進都要重做一次「哪些要砍」的判斷。一次性分支把那個判斷收斂成一次，代價只是分支會被刪 —— 而 tag 已經留住內容 |
| **另開 repo 放試玩版／產出物** | 解錯題。會出事的不是分支，是產出物的體積。而拆開之後「試玩版是 `main` 的哪個狀態砍出來的」這條線索會斷，得自己維護對照表 —— **手工對照表會腐爛** |
| **把 build commit 進 `demo/*` 分支** | git 物件庫是全 repo 共用的：**就算事後刪分支，物件仍留在每個人的 `.git` 裡**，要移除得改寫歷史。而且膨脹無聲 —— clone 變慢不會有人報錯 |
| **試玩版也用 semver** | 試玩版通常是「v0.3 的閹割版」，不是「v0.3 與 v0.4 之間」。硬塞進 semver 會讓版本號說謊，而版本號說謊沒有症狀 |
| **加一支 `branch-guard` hook** | 分支違規大多**會當場報錯**（受保護分支擋 push、合併衝突跳出來），不屬於「安靜壞掉」那一類。依本包自己的判準，**一個裝置要留下來得先說得出它擋掉了什麼** —— 這一個說不出來。有一條例外，見下 |
| **把分支設定寫進 [../../../core/安裝.md](../../../core/安裝.md)** | 那份承諾 20 分鐘裝完。分支是選用的，塞進去會拖垮那個承諾 |
| **在 `doc/` 加第五份正本** | 四份文件的分工是封閉的。分支規範是**流程規則**，與 commit body 規矩同一類 —— 那一條就不在四份裡，在 skill 裡 |

**這一輪唯一沒有機制的一條，要老實講**

`hotfix` 只合回 `stable`、忘了合回 `main` —— **這一條完全沒有症狀**。
下次 `main → stable` 發佈會把修正蓋回去，bug 原地復活，
而你會在使用者回報時才發現。

目前只在 [../../../core/分支與發佈.md](../../../core/分支與發佈.md) 把那一步標成
「最常被漏掉的一步」，那是**護欄，不是機制**。
真要機制化，該做的是發佈前檢查 `git log stable ^main` 有沒有東西，
而不是再加一個 hook —— 已列入待決問題。

**為什麼「切 demo 要寫一則決策」是這套裡唯一的額外要求**

試玩版的取捨（砍哪幾關、為什麼這個先不給人看）是純判斷。
diff 只看得到「刪了什麼」，看不到「為什麼這個留、那個砍」。
下次再做一版試玩時 —— 通常會有下次 —— 那是唯一救得回來的東西。

跟「commit body 要寫 `決策：X／因為 Y`」完全同構：
**把「為什麼」的產出時機，前移到還記得的那一刻。**

**如果錯了會怎樣**

- 兩條長命分支不夠用 → 症狀是「發佈前凍結期間沒地方開工」。
  那時再加 `release/*` 就好，現有規則不用推翻
- 一次性 demo 太麻煩 → 症狀是「同一場試玩要改三次，每次都重切」。
  那代表它其實是長期線，該改成平行分支
- 兩套 tag 造成混淆 → 症狀是有人問「demo-2026-09 是 v0.3 還 v0.4」。
  那時該補的是對照表，不是統一編號
