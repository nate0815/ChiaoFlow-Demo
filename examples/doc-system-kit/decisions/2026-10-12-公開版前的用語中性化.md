# 公開版前的用語中性化：連歷史紀錄一起改，並把這次破例記下來

**問題是什麼**

這個 repo 準備分裂出一份公開版。掃過一遍之後，內容沒有任何專案或組織的名稱，
但有三類東西不適合原樣公開：

| 類別 | 為什麼要處理 |
|---|---|
| 特定組織的內部資訊（某個 IT 支援頻道的名稱，3 處） | 對外人沒有用，而且是別人的內部資訊 |
| 預設讀者是「同一個組織裡的人」的語氣（約 20 處） | 公開版的讀者是協作者與合作對象，不一定在同一個組織裡，讀起來像內部文件外流 |
| 來歷寫得太含糊 | 讀者會誤以為這是替某個組織做的。實情是它歸納自個人 side project |

另外缺兩樣公開 repo 該有的東西：授權檔，以及給不讀中文的人的一段摘要。

**選了什麼**

| 決定 | 內容 |
|---|---|
| 用語 | 一律改成中性說法：受管電腦／管理員／協作者／合作對象／非公開資料／既有範本 |
| 範圍 | **全 repo，包含 `devlog/`、`decisions/`、`gotchas/`**（7 個歷史檔、9 行） |
| 「內容不要離開…」這條判準 | 改名為「內容不要離開你的機器」。判準本身沒變，擋的還是同三件事 |
| 來歷 | 改寫成實情，並補上「後來的專案多半沿用同一套、缺口從那裡回流」 |
| 授權 | MIT，新增 `LICENSE` |
| 手冊開頭 | 加一段英文摘要與一張流程圖 |

**為什麼這次破例改歷史紀錄**

這套規則自己寫的：時序 entry、決策、踩坑**只追加不改寫**。這次改了，所以要講清楚邊界。

「只追加」保護的是**當時做了什麼、為什麼這樣決定** —— 事後潤飾會讓理由看起來比當時更周全。
這次動的是**稱呼**：把指涉讀者與環境的詞換成中性說法，每一則的決定、理由、沒選的路都沒有變。

主事者的裁決是全 repo 一致。理由是公開版會被當成範例直接閱讀，
現在式文件與歷史紀錄用兩套稱呼，讀者會以為那是兩種不同的對象。

**這不構成往後可以改寫歷史的先例。** 判準是：改的是稱呼還是內容。
內容要更正，照舊追加一則新的、用 `supersedes` 指回去。

**為什麼授權選 MIT**

[extras/README.md](../../../extras/README.md) 選工具的第一條判準就是「授權能不能傳給別人」，
而且因此否決過候選。自己的 repo 沒有授權檔，等於拿一條自己沒通過的判準去篩別人。

**沒選的路**

| 沒選 | 為什麼 |
|---|---|
| **直接把這個 repo 轉成公開** | 舊 commit 裡還有那個頻道名稱與原本的用語。改掉現在的檔案擋不住別人翻歷史 |
| **公開版另外維護一份改寫過的內容** | 兩份一定會分岔。所以先在這裡改到可以公開，公開版只是它的一個乾淨快照 |
| **歷史紀錄維持原樣** | 第一版是這樣做的，經主事者裁決後改掉，理由見上一節 |
| **整份手冊翻成英文** | 維護兩種語言的成本高於目前的收益。先放摘要，有人問再說 |

**如果錯了會怎樣**

- 中性用語讓在受管電腦上的讀者找不到自己 → 症狀是有人問「配發的電腦能不能裝」。
  「受管電腦」第一次出現的地方已寫明是由組織配發、沒有管理員權限的機器，不夠再補
- 這次破例被當成先例 → 症狀是之後又有歷史檔被就地改寫而沒有對應的決策。
  上面那條「稱呼還是內容」的判準就是為了擋這個
