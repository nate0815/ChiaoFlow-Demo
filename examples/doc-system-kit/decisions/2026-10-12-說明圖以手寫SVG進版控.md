# 說明圖以手寫 SVG 進版控，放在用到它的文件旁邊

**問題是什麼**

這個 repo 幾乎全是文字。第一次來的人要讀完五百多行手冊，才拼得出
「誰觸發誰、誰擋誰、哪一份文件由誰寫」的全貌。

2026-08 做過一份說明簡報，裡面有幾張圖解釋得很清楚，但圖只存在於簡報裡。
之後機制改了五輪（雙工具適配、守則改成 `AGENTS.md`、README 規範、美術指南、分支模型），
簡報沒有跟上，也沒有任何東西提醒 —— 正是手冊第 0 節講的那種病。

**選了什麼**

| 決定 | 內容 |
|---|---|
| 圖放哪 | `core/圖/`（八張）與 `extras/圖/`（一張），跟用到它的文件放在同一個資料夾 |
| 格式 | 手寫 SVG。不引用外部字型與資源，GitHub 與編輯器預覽直接顯示 |
| 每張圖 | 都有 `<title>` 與 `<desc>`，用文字把圖的內容講一遍 |
| 嵌在哪 | 手冊、`core/安裝.md`、`core/分支與發佈.md`、`extras/README.md` 對應的章節 |
| 一覽 | `core/README.md`「圖一覽」：每張圖回答什麼、用在哪 |
| 簡報 | 之後的簡報從這裡取圖，**repo 是完整版，簡報是它的節錄** |

**這跟「還要繼續改的圖留 Mermaid」有沒有衝突**

[extras/README.md](../../../extras/README.md) 的分界是：還要繼續改的留純文字原始碼，
要交出去的才轉成正式圖。那條分界要保住的是四件事 ——
**純文字、進版控、diff 得出來、AI 讀得到**。

手寫 SVG 四件都滿足：它本身就是文字檔，改一條線在 diff 裡看得到是哪一條；
`<desc>` 讓 AI 不必解析座標也讀得到內容。所以這些圖算「原始碼」那一側，不算產出物。

沒有用 Mermaid 的理由是版面：這幾張圖有區域框、三種語意的連接線、圖例，
Mermaid 的自動排版排不出可以放在手冊開頭的樣子。

**沒選的路**

| 沒選 | 為什麼 |
|---|---|
| **全部用 Mermaid** | 排版不受控。第一版手冊開頭放過一張 Mermaid 流程圖，資訊對，但看起來像草稿 |
| **放 PNG** | 看不出改了什麼，AI 讀不到，而且每次改都要重新匯出 |
| **圖只放在簡報裡** | 已經發生過一次：簡報過時了而沒人發現 |
| **開一個根目錄的 `assets/`** | 手冊說這個 repo 是「四個資料夾，各一個概念」。圖是 Core 與 Extras 各自的一部分，不是第五個概念 |
| **用產圖工具每次重產** | 產出的樣式會隨工具版本變動，而且原始檔不在 repo 裡的話，下一個人改不了。這次的原圖就是這樣遺失的 |

**如果錯了會怎樣**

- 圖沒跟上機制的修改 → **不會有任何工具報錯**，這是這個做法最大的風險。
  目前只有文字護欄：`core/README.md`「圖一覽」提醒改流程時掃一遍。
  真要機制化，該做的是把 `core/圖/` 加進連結檢查那一類的定期檢視，不是再加一個 hook
- 手寫 SVG 改起來太痛 → 症狀是有人寧可不改圖。那時再考慮把座標抽成產圖腳本進版控
