# 2026-09-12（週六）— Day 30：讓 starter 同時吃 Claude Code 與 Codex CLI

**做了什麼**

起點是一個問題：「之後要 Codex 跟 Claude 共用這套文件機制，該調整還是另開一個
Codex 專用 repo？」查證之後答案很明確 —— **共用**，因為耦合比看起來小得多。

- 抽出 `core/starter/AGENTS.md` 當守則正本（工具中立），`CLAUDE.md` 縮成
  `@AGENTS.md` 匯入 ＋ 兩句 Claude 專屬補充
- hook 腳本與 `doc-sync` 正本移到工具中立的 `core/starter/.agents/`，
  `.claude/skills/doc-sync/SKILL.md` 改成四行 stub
- 新增 `core/starter/.codex/config.toml`（註冊 Stop 與 PreToolUse 兩個 hook）
- 新增 `core/starter/.agents/hooks/design-guard.mjs` —— Codex 版的權威層
- `.gitignore` 加 `doc/.design-unlock` 與 `.codex/*.local.toml`
- 全 repo 文件對齊：`README.md`、`core/安裝.md`（改成雙軌）、`core/README.md`、
  `setup/README.md`、`extras/README.md`、MCP／圖表／簡報／VSCode 四份標明工具歸屬
- 新增 `setup/CodexCLI環境.md`

**決策**

- [同一份 starter 同時支援 Claude Code 與 Codex CLI，不另開 repo](../decisions/2026-09-12-雙適配-Claude-與-Codex.md)
  —— 決定性的事實是 **Codex 的 Stop hook 契約與 Claude 相同**，`doc-sync-check.mjs`
  一個字都不用改就兩邊共用。另開 repo 要維護兩份 SOP，而漂移不會有任何工具報錯。

**踩到的坑**

- [Codex 的 PreToolUse 寫了 `"ask"` 不會報錯，但規格正本完全沒被保護](../gotchas/2026-09-12-Codex-的-PreToolUse-不支援-ask.md)
  —— 官方標示 *parsed but not supported yet*。改用「硬擋 ＋ `doc/.design-unlock` 解鎖檔」。
- 寫 `design-guard.mjs` 時第一版漏掉 Windows 路徑：`JSON.stringify` 會把 `\` 轉義成 `\\`，
  分隔符的字元類只吃一個就比對不到。13 個情境的測試矩陣裡就是這一條掛掉，
  改成 `[/\\]+` 後全過。**如果沒把 Windows 形式寫進測試，這條會安靜地漏到使用者那邊。**

**卡在哪**

**本機沒有安裝 Codex CLI**（`~/.codex` 是別的工具留下的，沒有 `config.toml`），
所以三個值沒辦法實機驗證：`CODEX_PROJECT_DIR` 存不存在、檔案寫入工具的 `tool_name`、
`.agents/skills/` 會不會被掃到。

處理方式是**標記而不是假裝**：`.codex/config.toml` 與 `core/安裝.md` 各留
`⚠ 待實機確認`，`setup/CodexCLI環境.md` 開頭直接寫「這份有未實機驗證的部分」，
第 6 節給了探測步驟。`design-guard.mjs` 設計成「比對不到就放行」，
所以填錯的後果是擋不到而不是誤擋。

**下一步**

1. 裝上 Codex CLI，跑 `setup/CodexCLI環境.md` 第 6 節的探測，把三個值改成實際值，
   清掉 `⚠ 待實機確認` 標記與 TECH 收件匣裡對應那一條
2. 用 Codex 實跑一次驗證 A（改 DESIGN 要被擋、建解鎖檔後放行）
3. 確認 `.agents/skills/` 掃不掃得到，決定要不要補 `.codex/skills/` 的 stub

**這一輪最值得記的一件事**

原本以為「共用還是分家」是個架構取捨，查完才發現它是個**事實問題**：
兩邊的 Stop hook 契約碰巧一模一樣，所以最核心的那一層根本不用選。
真正需要設計的只有權威層那一處 —— 而那一處之所以要設計，
不是因為 Codex 少了什麼功能，是因為它少了那個功能**卻不會報錯**。

> ⭐ 兩次都撞到同一個形狀：`"ask"` 被解析但不生效、Windows 路徑比對不到，
> **失敗方式都是安靜通過**。這一包治的就是這種病，結果自己在實作時又踩了兩次。

## 追記（同日，Codex 實機驗證之後）

裝上 Codex CLI `0.154.0-alpha.6.2`，讓它掃過整包。**三個未知收斂成一個，
而且抓到一個我自己測不出來的 bug。**

**收斂掉的**

- ✅ `.codex/config.toml` 可被嚴格解析
- ✅ `.agents/skills/doc-sync` 會出現在 model-visible skills 清單
  —— **不需要 `.codex/skills` stub**，原本的條件分支可以刪掉
- ✅ 兩支 hook 的行為在 fixture 裡都正確

**抓到的真 bug：`matcher` 列舉工具名 → 整個漏擋**

原本寫 `matcher = "apply_patch|edit|write|shell"`，但這版 CLI 的命令工具叫
**`exec_command`**。matcher 在 hook 被呼叫**之前**過濾，所以用 shell 改
`doc/DESIGN.md` 根本不會觸發 `design-guard.mjs`。

最值得記的是**為什麼自己測不出來**：單測是直接餵 stdin 給腳本，
**繞過了 matcher**，所以 13 個情境照樣全綠。
已改成 `matcher = ".*"`，過濾只留在腳本裡。詳見
[../gotchas/2026-09-12-matcher-列舉工具名會整個漏擋.md](../gotchas/2026-09-12-matcher-列舉工具名會整個漏擋.md)。

**被指出的過度宣稱：解鎖檔不是安全邊界**

初版在 `design-guard.mjs` 檔頭與多份文件寫了「AI 自己建不出來」。
那是錯的 —— 有 shell 與寫入權限的 agent 可以自己 `touch doc/.design-unlock`。

做了兩件事：
1. **補防線** —— guard 現在也擋「用工具建立解鎖檔」，且該檢查必須排在
   shell 快速放行之前（`touch` 不會命中「針對 DESIGN.md 的寫入跡象」，會被放掉）
2. **改措辭** —— 全部改成「協作慣例與防呆，不是安全邊界」，
   並寫明它擋的是「忘記」與「順手」，不是惡意

第 2 件比第 1 件重要。**一個被描述成安全邊界的防呆，比沒有防呆更危險** ——
人會依賴它。

**Codex 提的第四點：Stop hook 只看工作區**

先 commit 再收工的話工作區是乾淨的，擋不到。
這一條**本來就寫在 [../../../README.md](../../../README.md)「已知邊界」裡**，
不是新發現 —— 算是文件寫對了的一個旁證。

**順手清掉的東西**

驗證時 `CODEX_HOME` 被指向 `core/starter/.codex/`，Codex 把它當成自己的 home，
在裡面生了 sqlite、logs、`installation_id`、`shell_snapshots/` 一大包。
那些會被 `cp -r starter/. <專案>/` 一起複製出去。已刪除，並在 starter 的
`.gitignore` 補一整段擋掉，`setup/CodexCLI環境.md` 也加了「不要把 CODEX_HOME
指向專案 `.codex/`」的警告。

**剩下的唯一未知**

`${CODEX_PROJECT_DIR}` 是否存在。當時 session 連不到 OpenAI 端點，走不到 Stop 階段。
兩個 hook 都靠它定位腳本，**不存在的話會無聲失效** —— 這是下一步第一優先。

**這一輪最值得記的一件事**

> ⭐ **要驗一個攔截機制，必須用真的攔截路徑驗，不能只驗被攔截的那支腳本。**

我的 13 個情境測的是「腳本收到請求後會不會擋」，但真正的問題出在
「請求根本沒送到腳本」。單測的邊界剛好切在 bug 的上游，所以永遠測不到。

這跟今天稍早記的兩個坑是同一個形狀 —— `"ask"` 解析得過但不生效、
matcher 濾掉就不呼叫 —— **全部都是安靜通過**。三次了。

## 同日第二段：補上分支模型

**做了什麼**

- 設計了一套分支維護規則並寫進文件體系：`main`（開發）／`stable`（已發佈）兩條長命分支，
  其餘全部短命；命名 `<type>/<slug>`，**type 與 commit type 共用同一套字彙**
- 加了遊戲專用的 `demo/*`：一次性，切 → 減 → 封 → 打 tag → 刪分支，**不合回任何地方**
- tag 定成兩套：正式版 semver `v0.3.1`，試玩版 `demo-<YYYY-MM>-<場次>`
- 新增 [../../../core/分支與發佈.md](../../../core/分支與發佈.md)（人的操作手冊 ＋ 為什麼），
  規則正本放 [../../../core/starter/AGENTS.md](../../../core/starter/AGENTS.md) 的「分支與發佈」
- starter 的 `.gitignore` 補了一段 build 產出物，帶理由註解
- 手冊加了第 11 節講為什麼

**決策**

- [兩條長命分支 ＋ 一次性試玩分支，產出物不進 git](../decisions/2026-09-12-分支模型與發佈流程.md)
  —— 排除了 GitFlow、長期平行 demo 分支、另開 repo 放產出物三條路，理由在該檔

**卡在哪／踩到什麼**

這一輪沒有踩坑，但有兩個**判斷**卡了一下，值得記：

- **正本該放哪。** 一度想開第五份正本放進 `doc/`，但四份文件的分工是封閉的。
  最後認定分支規範是**流程規則**，與 commit body 規矩同一類 ——
  而那一條本來就不在四份文件裡，在 skill 裡。於是正本放 `AGENTS.md`
  （下游 AI 讀得到的唯一一份），`core/分支與發佈.md` 只放操作與為什麼，**用連結指過去不複製表**
- **新章節放哪。** 手冊的 §11 是**附加在最後**的，不是插進「已知邊界」前面 ——
  因為本包自己第 9 節就寫著跨檔章號位移不會報錯，而 2026-08-28 重排章節時
  已經踩過一次（五處外部引用中招）。**自己的規矩要對自己生效**

**這一輪刻意沒做的事**

沒有加 `branch-guard` hook。依本包自己的判準 ——
**一個裝置要留下來，得先說得出它擋掉了什麼** —— 分支違規大多會當場報錯
（受保護分支擋 push、合併衝突跳出來），不屬於「安靜壞掉」那一類。

**下一步**

- `stable` 分支**還沒建**。那是「現在的 main 算不算發佈過」的判斷，
  該由人決定時點，不該由一次文件變更順手做掉。建立指令已寫在 `core/分支與發佈.md`
- 待決問題新增一條：hotfix 漏合回 `main` 是這套規則裡唯一沒有症狀的一條

**這一輪最值得記的一件事**

> ⭐ **慣例早就存在，缺的不是慣例，是「它被寫下來」這件事本身。**

`git log` 裡四個分支名稱形狀完全一致，`feat/` `chore/` 用了好幾個月 ——
所以這一輪不是「設計一套新規則」，是**把一個已經在跑、但只存在於記憶裡的東西固定住**。

差別在第二個人（或第二個 AI）進來的那一刻：慣例只能靠猜，而**猜錯不會報錯**。
這跟今天稍早那三次「安靜通過」是同一個家族 —— 只是這次壞的不是腳本，是人的記憶。
