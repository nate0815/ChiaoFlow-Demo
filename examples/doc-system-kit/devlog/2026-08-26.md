## 追加（同日稍晚）— 周邊工具：圖表與簡報

**做了什麼**

- `sop/` 新增三份（B 組）：[圖表工具.md](../../../extras/圖表工具.md)、
  [簡報製作.md](../../../extras/簡報/製作.md)、[VSCode外掛.md](../../../extras/VSCode外掛.md)
- `sop/README.md` 索引改成 A 組（文件體系）／B 組（產出物工具）兩組，兩組互不依賴
- 手冊新增 §12，講「為什麼一份講文件的手冊要管圖與簡報」

**決策**

- [周邊工具選型](../decisions/2026-08-26-周邊工具選型.md)
  —— 判準只有兩條（**授權能不能傳給別人**、**受管電腦裝不裝得起來**），
  這兩條否決掉了功能最強的候選（官方 pptx skill）。
  代價是這套組合產不出可編輯的 `.pptx`，已明寫在 SOP 裡不迴避

**觀察**

- §10 的原則（「看不到的東西 AI 也看不到」）往下游推一格就成立於交付：
  Mermaid 貼進 PowerPoint 會消失、節點一多沒人讀得懂、轉圖時被砍掉節點 ——
  後兩種**一樣沒有症狀**，跟 §0 的第三種病同一個家族
- 因此 B 組的核心分界是一句話：**這張圖是還要繼續改的原始碼，還是要交出去的產出物？**
  前者留 Mermaid，後者才轉。不要全面消滅 Mermaid

**下一步**

- B 組的工具清單會過期（版號、星數、外掛授權條款）。維護規則寫成「整段重測重寫，
  不要逐行改」—— 逐行改一定會漏，而漏掉不會有工具報錯

## 再追加 — 補上 0 組（地基）SOP

**做了什麼**

- `sop/` 新增兩份（0 組）：[ClaudeCode環境.md](../../../setup/ClaudeCode環境.md)、
  [Python環境.md](../../../setup/Python環境.md)
- 索引改成 **0 組（地基）／A 組（文件體系）／B 組（產出物工具）** 三組；
  前置需求表加一欄「**要管理員權限嗎**」—— 整份需求裡只有 Node.js 那一項要
- frontend-slides 從「建議」升為**選定的主線**，補上第一次怎麼餵它、挑風格那一步要注意什麼

**卡在哪／踩到什麼**

- [`python` 與 `python3` 不是同一個](../gotchas/2026-08-26-python-與-python3-不是同一個.md)
  —— 實測本機三個 Python 並存，`python`=3.12.10、`python3`=3.14.5，套件目錄不通。
  而工具文件習慣寫 `python3`（Linux 慣例），照貼就跑到另一個直譯器上

**觀察**

- 寫 0 組時才發現前置需求真正該分的不是「要不要裝」，而是**「要不要管理員權限」** ——
  對受管電腦的使用者來說，那才是「這件事我做不做得到」的分界。
  整套需求裡只有 Node.js 落在要申請那一側，講清楚這件事讓申請容易得多
- 這次三份 SOP 的坑（`python3` 指向、JSON 單反斜線、權限白名單的中文亂碼）
  **全部是「錯誤訊息指向錯方向」那一類**，跟 §0 的第三種病同源。
  三份文件的踩坑清單因此都把「現象」與「原因」分成兩欄寫

**驗證**

- frontend-slides **實際裝起來跑過驗證**（`claude plugin install`，2.1.0，scope: user）——
  文件裡的觸發指令 `/frontend-slides:frontend-slides`、七個階段、34 套版型與三支腳本，
  都是從安裝後的檔案讀出來的，不是照抄上游 README
- ⚠️ 這件事本身值得記：前一輪寫 SOP 時**只讀了上游文件沒實裝**，
  流程寫成「五步」（上游 README 的簡述），實際是七個階段。
  **照抄別人的 README 會產生看起來對、但對不上實物的說明**

**下一步**

- 版號與量測值（Python 版本、CLI 版號、外掛清單）維護規則一致：
  **整段重測重寫，不要逐行改**

## 三追加 — skill 怎麼被叫到，補進 ClaudeCode 環境 SOP

**做了什麼**

- [ClaudeCode環境.md](../../../setup/ClaudeCode環境.md) 的第 5 節從「放在哪」擴成
  「放在哪、怎麼被叫到」：自然語言 vs 斜線指令、什麼時候該改打斜線、
  為什麼會漏叫、常駐 vs 觸發的 token 成本、重複安裝怎麼查
- 踩坑清單加兩條（「裝了卻沒被用到」「同一個 skill 裝了兩次」），檢查清單加兩項

**做法上的取捨**

- 新內容**開成 5.1～5.5 的子節，不新增頂層章號** —— 這樣 §6／§7／§8 都不位移，
  檔內既有的「看第 6 節」「第 4 節」全部不用改。
  正是 [DEVLOG.md](../DEVLOG.md) 技術評估那條「章號會安靜位移」要避開的東西

**觀察**

- skill 的 `description` 是**路由面**，不是簡介 —— AI 決定要不要載入時**只看得到那一行**，
  本體是決定要用了之後才載入。所以「skill 做得好不好」與「會不會被叫到」是兩件事
- 失敗形態一樣沒有症狀：沒被叫到時，AI 會用一般能力回一個看起來合理的答案，
  **不會有東西告訴你有個更適合的工具剛剛沒被叫到**。與 §0 第三種病同源
- diagram-design 把 39 種圖型名稱全列進 `description`，還寫 CI 擋「新增圖型沒改 description」——
  同一條原則：把「壞了不會報錯」換成「會報錯」

**待辦**

- 本機的 `diagram-design` 目前**使用者層與外掛層各一份、內容完全相同**（各 40117 bytes）。
  兩份都在付常駐成本。尚未清理
