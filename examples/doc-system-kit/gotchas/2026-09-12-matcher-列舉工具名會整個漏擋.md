# PreToolUse 的 matcher 列舉工具名，換一版 CLI 就整個漏擋，而且沒有症狀

**現象**

`design-guard.mjs` 自己測起來全對：13 個情境都正確，包含
`{"tool_name":"shell","tool_input":{"command":"echo x > doc/DESIGN.md"}}` 會被擋。

但**在真的 Codex CLI 裡，用 shell 改 `doc/DESIGN.md` 完全不會被擋**。
hook 有註冊、有被信任、腳本也沒壞 —— 它根本沒有被呼叫。

**原因**

`.codex/config.toml` 原本寫：

```toml
[[hooks.PreToolUse]]
matcher = "apply_patch|edit|write|shell"
```

實測 Codex CLI `0.154.0-alpha.6.2`，它的命令工具叫 **`exec_command`**，不是 `shell`。
matcher 是**在 hook 被呼叫之前**做的過濾，所以 `exec_command` 在進到腳本之前
就被濾掉了。

諷刺的是腳本內部**本來就處理得了** —— `WRITE_TOOLS` 寫成
`/patch|edit|write|apply|create|shell|bash|exec|command/i`，`exec_command` 命中兩次。
**過濾寫在兩個地方，嚴格的那個先執行，寬鬆的那個永遠沒機會跑。**

失敗方式是「安靜放行」：沒有錯誤、沒有警告，測試矩陣也照樣全綠，
因為單測是直接餵 stdin 給腳本，**繞過了 matcher**。

**解法**

matcher 改成全收，過濾責任只留在腳本裡：

```toml
[[hooks.PreToolUse]]
matcher = ".*"
```

腳本第一件事就是比對 `WRITE_TOOLS`，不像寫檔就立刻 `exit 0`，成本可以忽略。

**可以帶走的判準**

> **同一個過濾條件不要實作在兩層。** 如果一定要，讓**外層寬、內層嚴** ——
> 反過來的話，外層會安靜地吃掉內層的判斷，而你的單測看不到外層。

這與本包「同一件事不寫在兩處」是同一條原則，只是換到了設定與程式之間。

**這個坑是怎麼被抓到的**

不是自己測出來的 —— 是拿真的 Codex CLI 掃過一遍才浮出來。
單測餵的是我**以為**的工具名，所以永遠會過。
**要驗一個攔截機制，必須用真的攔截路徑驗，不能只驗被攔截的那支腳本。**
