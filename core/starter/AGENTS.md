## 5. 文件的物理形態

**Obsidian 是可選的閱讀器，不是這套體系的地基。** 沒有它，`doc/` 用 git ＋ grep
一樣完整運作 —— 所以不要寫出「只有在 Obsidian 裡才成立」的東西。

| 規矩 | 說明 |
|---|---|
| **跨檔引用寫相對路徑 Markdown 連結** | `[某決策](decisions/2026-08-26-xxx.md)`。**不要用 `[[wikilink]]`** —— 它不帶路徑，你只能用檔名去猜是哪一個，vault 裡一有同名檔就歧義，而且 GitHub 與編輯器都點不開 |
| **指向章節時寫標題，不寫章號** | `TECH「不變式」` 而非 `TECH §5`。章號會因為前面插一節就整批位移，而**沒有任何工具會報錯** |
| **專有名詞與程式碼一字不差** | 文件寫 `PlayerController` 就不要在別處寫「玩家控制器」。命名不一致會大幅降低搜尋命中率 |
| **標題結構要能當定位錨點** | 階層明確的 `##` / `###`。`grep -n '^## '` 是最常用的定位方式 |
| **Dataview／Bases 的產出不是正本** | 那是 render 時才算出來的，檔案裡只有查詢語句。你讀到的是**零筆資料，而且不會報錯** —— frontmatter 才是正本 |

> **一條判準管住全部**：關掉 Obsidian、用記事本打開那個檔，
> **看不到的東西，你也看不到。**

## 6. 分支與發佈

> ⚠️ **移植時要改這張表**：沒有試玩版的專案把 `demo/*` 那列刪掉；
> 還沒發佈過任何東西的專案可以先不要有 `stable`，等第一次發佈再建。
> **刪掉的列要真的刪掉**，留著會讓人以為那條線存在。

人的操作步驟（怎麼建 `stable`、發佈怎麼跑、要不要另開 repo）不在這裡 ——
那是給人讀的，本檔只放你要遵守的規則。

### 6.1 分支表

| 分支 | 角色 | 從哪開 | 合回哪 | 壽命 |
|---|---|---|---|---|
| `stable` | **已發佈的內容** —— 使用者手上跑的就是這個 | —— | —— | 永久，**不直接 commit** |
| `main` | **主要開發分支**，整合點。保持隨時可跑 | —— | → `stable`（發佈時） | 永久 |
| `feat/<slug>` | 新功能 | `main` | → `main` | 短命，合併後刪 |
| `fix/<slug>` | 修 bug（非緊急） | `main` | → `main` | 短命，合併後刪 |
| `hotfix/<slug>` | 已發佈版本的緊急修正 | **`stable`** | → `stable` **且** → `main` | 短命 |
| `demo/<場次>` | **試玩版輸出**：刪減與封裝 | `main` | **不合回任何地方** | 一次性，打完 tag 就刪 |
| `docs/<slug>` `chore/<slug>` `refactor/<slug>` | 其餘雜項 | `main` | → `main` | 短命 |

**命名**：`<type>/<英文-kebab-slug>`。type 與 commit message 的 type
**共用同一套字彙**（`feat` `fix` `docs` `chore` `refactor`），另加 `hotfix`
與 `demo` 兩個分支專用的。一套字彙管兩個地方，不必記兩套。

⛔ **不要在 `main` 或 `stable` 上直接開工。** 要動手就先開分支 ——
包含只改一行的情況。

### 6.2 三條護欄

| 護欄 | 違反的話會怎樣 |
|---|---|
| **`hotfix` 一定要合回 `stable` 與 `main` 兩邊** | 只合 `stable` 的話，下次 `main → stable` 發佈會把修正**蓋回去**，bug 原地復活，而且不會有任何東西報錯 |
| ⭐ **`demo` 分支只做減法與封裝，不做加法** | 見下 |
| **build 產出物不進 git** | git 的物件庫全 repo 共用：一包 build commit 進去，就算事後刪分支，那些物件仍然留在每個人的 `.git` 裡。`demo/*` 放的是**產生試玩版的設定**，不是試玩版本身 |

**`demo` 分支上可以做的**：關功能旗標、砍內容範圍、改 build 設定、換標題畫面。
**不可以做的**：寫新的遊戲邏輯、修 `main` 也有的 bug。

因為 `demo` 不合回任何地方，寫在那裡的東西會**隨分支一起消失** ——
而它消失的時候不會有任何症狀。要修 `main` 也有的 bug，去開 `fix/*`。

> **可執行的判準**：`demo` 分支上的 diff，如果拿掉之後 `main` 會少一個功能，
> 那它就走錯分支了。

### 6.3 tag 命名：兩套，刻意不混用

| 用途 | 格式 | 打在哪 |
|---|---|---|
| 正式版 | `v<major>.<minor>.<patch>`，例 `v0.3.1` | `stable` |
| 試玩版 | `demo-<YYYY-MM>-<場次slug>`，例 `demo-2026-09-taipei` | `demo/*` 的最後一個 commit |

試玩版通常是「v0.3 的閹割版」，不是「v0.3 與 v0.4 之間的東西」。
硬塞進 semver 會讓版本號說謊 —— 而**版本號說謊是沒有症狀的**。

> ⚠️ [doc/DESIGN.md](doc/DESIGN.md) 版本紀錄裡的 `v0.3` 是**文件內部版本**，
> 跟 git tag 的 `v0.3.1` **是兩套編號**。兩者不對齊，也不該對齊 ——
> 不要為了讓它們看起來一致而去改任何一邊。

### 6.4 哪個時機要動文件

| 時機 | 文件動作 |
|---|---|
| 開 `feat/*` | **無**。不要為了開分支先寫文件 |
| 合回 `main` | 照舊收工回填（收工檢查會擋） |
| `main → stable` 發佈 | 規格有動才 bump DESIGN／PLAN 版本紀錄 ＋ `doc/devlog/` 記一則，**寫上 tag 名**；順便照 `README.md` 的「怎麼跑起來」實跑一次 —— 那段最容易在不知不覺間失真 |
| ⭐ **切 `demo/*`** | `doc/decisions/` 開一則：**這次試玩砍了什麼、為什麼砍** |
| 刪 `demo/*` | 先確認 tag 打了 —— tag 是那則決策的證物，分支刪掉後它是唯一撈得回內容的路 |

**為什麼切 `demo` 要寫一則決策**：試玩版的取捨（砍哪幾關、為什麼這個先不給人看）
是純判斷。diff 只看得到「刪了什麼」，看不到「為什麼這個留、那個砍」。
下次再做一版試玩時，這是唯一救得回來的東西。
