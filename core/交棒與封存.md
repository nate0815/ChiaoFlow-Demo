# prototype 的生命週期：交棒與封存

> **選用。** 只有在 prototype 要結束、東西要交給正式流程或收攤時才需要讀。
> 為什麼這套體系最適合 prototype，見 [../README.md](../README.md)「這套東西解決什麼問題」。

ChiaoFlow 抽自一個 prototype，也最適合那個場景 —— 手冊裡「什麼時候值得用」
描述的「連續幾週動同一份程式、有值得留的判斷」，正是 prototype 的形狀。
而 prototype 會結束 —— 結束的時候要處理兩件事。

---

## 1. 與正式規格流程是接力，不是並行

如果你的團隊另有一套正式規格文件流程，**不要試圖把兩者整合成一套。**
範圍、受眾、節奏三個基數都對不上：正式規格是一個 repo 裝多個專案、給不用 git 的人看網頁、
以功能為單位走審查；這套是移植進每個專案、給 AI 讀原始檔、以一次收工為單位擋。

而且兩邊的核心機制對彼此完全無用 —— 收工 hook 裝進規格 repo，企劃改一句話就被擋。

需要的不是整合流程，是**交棒時交什麼**。

---

## 2. 交棒清單

| 交 | 不交 |
|---|---|
| DESIGN 的「要驗證的假設」與「健檢」—— 這是 prototype 的核心產出：哪些假設成立、哪些不成立 | `TECH.md` —— 正式開發會重寫 |
| DESIGN「已排除的方案」＋ PLAN「已排除的技術路線」＋ `decisions/` 全部 | 時序 entry —— 流水帳 |
| DESIGN 的規格本體（當正式規格的原料） | |

⚠️ **數值要標明是假值還是定案值。** Prototype 交棒時最常見的失真，
就是假值被當成定案值抄進正式規格。

第二列是最重要的 —— **「這條路試過，不行」是唯一無法從別處重建的東西**，
而正式規格的範本通常沒有欄位放它。沒有的話，去加一節。

---

## 3. 封存原則：一律封存，不捨棄

**Prototype 交棒後封存，不要刪除。** 三個理由：

1. **這套體系自己的原則就是反對刪除** —— 定期精簡是用今天的認知重寫當時的認知
2. **commit body 那筆投資會整包作廢。** 整套設計是把「為什麼」前移到 commit body ——
   那些理由**提取不出來**，它們散在 `git log` 裡、沒有結構、不在四份文件裡
3. **提取是單向且有損的，封存的成本近乎零。** 「當初是不是試過這個」這種問題，
   repo 還在是 30 秒的事；捨棄了不是貴，是**不可能**

封存要做對三件事，否則等於捨棄：

| 做 | 為什麼 |
|---|---|
| **原地凍結、打 tag，不要搬走** | git repo 本身就是封存格式。搬到共用磁碟或壓成 zip = 斷開 git 歷史 = 丟掉理由 2 那筆投資 |
| **每份文件的 frontmatter 加 `archived` 與 `superseded-by`** | 半年後有人是 grep 到某個檔進來的，不是從 README 進來的。**寫 frontmatter 不動內文，所以不違反「只追加不改寫」** |
| **正式規格那側要有回鏈** | 沒有這條連結，封存的東西永遠不會被打開 |

封存後**不准再改**。被偷偷改一行，比留著危險得多。

**可以捨棄的唯一情況**：`decisions/` 與 DEVLOG「技術評估」都是空的 ——
那代表這輪探索沒有可陳述的結論，刪掉沒有損失。
