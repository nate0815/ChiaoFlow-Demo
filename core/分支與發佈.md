# 分支與發佈

> **選用。** 只有在專案要開始分線開發、或要推出版本時才需要讀。
> **規則正本不在這裡** —— 分支表、護欄、tag 命名在
> [starter/AGENTS.md](starter/AGENTS.md) 的「分支與發佈」那一節，因為那一份會被
> 複製進你的專案，是 AI 讀得到的唯一一份。**本檔不複製第二份表**，
> 只講**為什麼這樣切**，以及**人要做的操作**。

裝完 Core 之後，文件那側已經有規矩了（怎麼寫、怎麼回填、收工怎麼擋），
但 git 那側還是空的。這一份補的就是那一塊。

---

## 1. 為什麼需要寫下來

分支慣例有一個特性：**它通常已經存在，只是沒人寫下來。**

翻一下 `git log`，你多半會發現分支名稱早就有固定形狀了 —— 問題是它只存在於
「上次是怎麼做的」這個記憶裡。於是會發生三件事：

| 症狀 | 什麼時候會痛 |
|---|---|
| 隔了三個月回來，忘記上次是 `feature/` 還是 `feat/` | 分支列表開始兩種並存，篩選與自動化都失準 |
| 多一個人（或多一個 AI）進來，用了另一套 | 合併順序開始靠問，不靠看 |
| 要發版了，才發現沒有一條線代表「已經發出去的東西」 | **最痛的一次**，通常發生在要修線上 bug 的當下 |

第三種是 `stable` 存在的理由 —— 沒有它的話，「使用者手上跑的是哪一版」
只能靠回想哪一個 commit 發出去過。

---

## 2. 兩條長命分支，不是三條

![分支模型：兩條長命分支，其餘都是短命分支](圖/分支模型.svg)

ChiaoFlow 建議的模型只有兩條永久分支：`main`（開發）與 `stable`（已發佈）。
功能、修正、試玩版都是短命分支。

**為什麼不用 GitFlow 那套（多一條 `develop` 與 `release/*`）**：
`release/*` 那一層是為了解決「發佈前要凍結、但同時得繼續開發下一版」的並行需求。
個人與小團隊沒有這個並行 —— 你不會一邊凍結一邊開工，你就是那個人。
加了只是多一層每次發佈都要維護的東西，而它擋不掉任何實際會發生的錯誤。

**什麼時候該加回來**：當「發佈前的驗證」長到需要好幾天、而那幾天你必須同時
開始做下一版的時候。在那之前它是純成本。

## 3. 操作：初次建立 `stable`

`stable` 代表「已經發出去的內容」，所以**建立它的時機是第一次發佈**，
不是裝完 Core 的當下。太早建的話它只是 `main` 的一個空殼別名。

第一次發佈時：

```bash
git checkout main
# 先確認 main 是可跑的狀態

git checkout -b stable
git tag v0.1.0
git push -u origin stable
git push origin v0.1.0
```

之後 `stable` 就再也不從 `main` 重建了 —— 一律用合併（見下一節）。

> **遠端如果有分支保護**（GitHub／GitLab 都有），把 `stable` 設成受保護分支、
> 禁止直接 push。這是唯一一處值得花兩分鐘設定的機制 ——
> 因為「不小心在 `stable` 上開工」是這套規則裡最容易犯、也最難察覺的一條。

---

## 4. 操作：發佈（`main` → `stable`）

```bash
# 1. 在 main 上驗證通過（這一步沒有捷徑）

# 2. 規格若有動，先 bump doc/DESIGN.md 或 doc/PLAN.md 的版本紀錄

# 3. 合併，一定要 --no-ff
git checkout stable
git merge --no-ff main -m "release: v0.3.1"

# 4. 打 tag
git tag v0.3.1
git push origin stable v0.3.1

# 5. 回 main，在 doc/devlog/<今天>.md 記一則，寫上 tag 名
git checkout main
```

**第 3 步的 `--no-ff` 是刻意的。** 讓 git fast-forward 的話，
`stable` 只會是一個往前滑的指標，歷史上**看不出「這一段是這次發的」** ——
而那正是你半年後想知道的事。`--no-ff` 留下一個合併點，
`git log --first-parent stable` 就是一份發佈清單。

**第 5 步不要省。** tag 名寫進 devlog 的 `commits:` 欄位，
是「這一版到底包含什麼」唯一撈得回來的路徑。

### 緊急修正（hotfix）

```bash
git checkout stable
git checkout -b hotfix/<slug>
# 修完、驗完

git checkout stable && git merge --no-ff hotfix/<slug>
git tag v0.3.2 && git push origin stable v0.3.2

git checkout main && git merge --no-ff hotfix/<slug>   # ⚠️ 這一步最常被漏掉
git branch -d hotfix/<slug>
```

⚠️ **最後那一步合回 `main` 是整套流程裡最常被漏掉的一步。**
漏了的話，下次 `main → stable` 發佈會把修正**蓋回去**，bug 原地復活，
而且不會有任何東西報錯 —— 你會在使用者回報時才發現。

## 5. 操作：切一版試玩（`demo/*`）

遊戲專屬的那一條線。流程是**切 → 減 → 封 → 標 → 刪**：

```bash
git checkout main
git checkout -b demo/2026-09-taipei

# 減：關功能旗標、砍內容範圍、改 build 設定、換標題畫面
# 封：build 出來，產出物丟發佈平台，不要 commit 進 git

git tag demo-2026-09-taipei
git push origin demo-2026-09-taipei     # 只推 tag，分支不必推

git checkout main
git branch -D demo/2026-09-taipei        # tag 已經留住內容了
```

**`demo/*` 不合回任何地方**，所以它上面只能做減法 ——
完整的判準與可以／不可以做的清單在 [starter/AGENTS.md](starter/AGENTS.md)
的「分支與發佈」，那裡是正本。

### 切 demo 之前，先寫一則決策

這是 ChiaoFlow 對試玩版唯一的額外要求：在 `doc/decisions/` 開一則，
寫**這次砍了什麼、為什麼砍**。

因為試玩版的取捨是純判斷 —— diff 只看得到「刪了什麼」，
看不到「為什麼這一關留、那一關砍」。下次再做一版試玩時（通常會有下次），
這是唯一救得回來的東西。跟 commit body 要寫 `決策：X／因為 Y` 是同一個道理。

## 6. 要不要另開 repo 管理？

**建議：原始碼不拆，但 build 產出物不要進 git。**

會問這個問題，通常是因為擔心「試玩版的東西混進主線」。
那個擔心是對的，但拆 repo 解錯了題 —— 真正會出事的不是分支，是**產出物的體積**。

### 為什麼不拆原始碼

| 理由 | 說明 |
|---|---|
| **分支不隔離儲存空間** | git 的物件庫是全 repo 共用的。把一包 WebGL／Unity build commit 進 `demo/*`，**就算事後刪掉分支，那些物件仍然留在每個人的 `.git` 裡**。要真的移除必須改寫歷史，所有協作者都得重新 clone |
| **膨脹是無聲的** | clone 變慢不會有人報錯，只會慢慢變成「這個 repo 有點難用」。等到有人抱怨時，那幾包 build 已經在歷史裡待了半年 |
| **拆了就對不起來** | 試玩版的價值在於「它是 `main` 的哪一個狀態砍出來的」。拆成兩個 repo，那條線索就斷了 —— 你得自己維護一張對照表，而手工對照表會腐爛 |

### 產出物該放哪

原始碼要 diff、要 merge、要 blame；build 只要「某個時間點的那一份」。
git 對後者沒有任何優勢，只有成本。所以：

- **發佈平台**（itch.io／Steam／GitHub Releases 的 release assets）—— 預設選這個
- tag 是 build 與原始碼之間的連結：`demo-2026-09-taipei` 這個 tag
  對應到平台上那一包，兩邊用同一個名字

### 真的該另開 repo 的兩種情況

| 情況 | 怎麼做 | 判準 |
|---|---|---|
| **美術原檔**（`.psd`／`.blend`／大量貼圖）由不用 git 的人維護 | 獨立 asset repo，或同 repo 用 Git LFS | **「這些檔會不會被 diff」** —— 不會的話，git 對它們就只有成本 |
| **試玩版要公開、原始碼要私有** | 把 build 放到公開的發佈平台 | 這其實**不是拆 repo**，是拆「原始碼」與「產出物」。多開一個 git repo 放 build 會同時踩到上面那三個問題 |

兩種情況拆的都是**產出物或素材**，不是原始碼本身。

## 7. 這個 kit repo 自己怎麼套

ChiaoFlow 這一包自己也照這套走，但有一處不一樣：

| 分支 | 在這個 repo 的定義 |
|---|---|
| `main` | 主要開發 |
| `stable` | **[安裝.md](安裝.md) 的三個驗證全部跑過**的 kit 版本 —— 判準明確、可驗證，不是「感覺穩了」 |
| `feat/*` `fix/*` `docs/*` `chore/*` | 照分支表 |
| `demo/*` | ⛔ **沒有這條。** 這個 repo 不出試玩版 |

最後一列要明講，否則照抄的人會以為每個 repo 都該有一條 `demo/*`。
**分支表是要按專案刪列的**，不是照單全收 —— 這也是為什麼
[starter/AGENTS.md](starter/AGENTS.md) 那一節開頭就標了「移植時要改這張表」。

> 這一份與 [交棒與封存.md](交棒與封存.md) 是同一條原則的兩個尺寸：
> **刪掉的東西要先打 tag。** 那一份講 prototype 結束時整包封存，
> 這一份講試玩分支刪掉前留 tag —— 理由都是「git repo 本身就是封存格式」。
